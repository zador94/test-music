# Репетиция — Android-прототип

Приложение: взять трек с телефона, один раз разложить нейросетью на **четыре дорожки**, играть под метроном. Если крутите BPM метронома — вместе с ним меняется скорость трека.

Это папка **проекта Android Studio**. Репозиторий: https://github.com/zador94/test-music. Версия **0.3.44**.

## Что реально стоит в этом срезе

**Модель: HT-Demucs (`htdemucs`), один ONNX-файл, 4 стемы.** Не mid/side, не 6-stem гитара.

| Файл | Что это |
| --- | --- |
| `stems/vocals.wav` | вокал |
| `stems/drums.wav` | ударные |
| `stems/bass.wav` | бас |
| `stems/other.wav` | «Музыка»: всё остальное, **включая гитару и клавиши** |

Порядок выходов модели: `drums, bass, other, vocals`. Веса: `htdemucs_fp16weights.onnx` (~166 МБ), ONNX Runtime CPU. Длинный трек идёт **окнами модели 7.8 с** с overlap-add как в 0.3.28: mix на диске, в RAM только текущий сегмент и кольцо аккумулятора, готовый STRIDE сразу в stem WAV. Внешний слой 30 с + линейный кроссфейд из 0.3.29 **убран** (помехи). Новые сплиты — **IEEE float32 WAV** 44.1 кГц. Плеер стемов **не** декодирует эти WAV через ExoPlayer: `StemMixMediaSource` отдаёт уже сведённый PCM 16-bit. Старые 16-bit WAV тоже читаются.

Mute вокала = gain 0 у вокала, на **следующем** смешанном буфере (десятки мс, либо `AudioTrack.getMinBufferSize` на эмуляторе), не через секунду очереди ExoPlayer. Гитара отдельно не выходит — она в «Музыке». Метроном: клик в **том же** PCM, что музыка, после WSOLA (`out[i] = music_after_stretch[i] + click[i − beat]` + limiter). Один AudioTrack, всегда 1×; относительная задержка клика и песни = 0. Один короткий клик на четверть, громкость `CLICK_VOLUME` 2.2 (не зависит от mute/solo/gain стемов). Сетка клика — **`beats[]` в µs**: плеер в `PlaybackEngine.applyKickGrid` → `setAnalysis` переводит секунды JSON × 1e6. `mixInto` красит в remaining() того буфера, который `MetronomeAudioSink` отдаёт в DefaultAudioSink/AudioTrack (курсор после paint возвращается). Если шаг сетки не четверть в µs **или** ни одна доля не лежит около текущего PTS стемов (± период) — решётка `periodSec`, как до 0.3.42. Song time той же шкалы, что стемы; клик после WSOLA, сам клик не растягивается. `TIME_UNSET` не рисует t=0. Ударные BPM не выбирают и не складывают 150→75. Подпись «Темп» — одно десятичное. Слайдер «Сдвиг клика, мс» (−500…+500, шаг 5 мс) — запас на задержку аппарата, не способ попасть в долю. По умолчанию **0** (ключ prefs `click_shift_ms_v37`, старый −180 не читаем).

После разбора пишется `tracks/{id}/analysis.json`. Для клика: **`periodSec`** и **`bpm`** из `tempoOfTrack` по миксу (`bpm` — до 0.1, только подпись); **`beats[]`** — черновая сетка `phase+n*period`, каждая доля притянута к novelty/кику в окне ±0.12 периода (нет онсета — точка решётки). `DrumPhase.align` не переписывает весь `beats[]` одним `phaseSec`: максимум origin/первая доля, snap к онсетам **микса**, не к телу drums.wav; `periodSec`/`bpm` не трогает. `downbeatOffset` — индекс доли 0..3, не секунды. Плеер читает `beats[]`. StemSplitWorker: `persistAnalysisFromMixWav` до стемов, второе сохранение `analysis.json` после `splitMixStreaming` через `DrumPhase.align(drums, mix)` (не `KickGrid.refine`). Кнопка «Пересчитать темп и фазу» пересобирает `beats[]` тем же snap. `kickGridVersion` **12** (не поднимали). Если нет `periodSec` или версия старше 12 — то же при открытии.

## Почему 0.3.9 крашилось при включении клика

`ClickTrack` читал `ExoPlayer.currentPosition` / `playWhenReady` с потока `metronome-click`. Media3 разрешает плеер только с одного потока (main) → `IllegalStateException` → процесс умирает в момент Switch метронома. С 0.3.10 часы клика — снимок с main (`ClickClock`: songTime = origin + elapsed × speed), worker ExoPlayer не трогает.

## Почему 0.3.8 метроном всё ещё не слышно

До 0.3.8 Android писал клик в тот же PCM, что стемы (`mixInPlace` в `MetronomePcmPipe`). На устройстве этот буфер часто не доходил до колонок: `isPcm==false` (mime не `audio/raw`, `pcmEncoding=NO_VALUE`) — mix не вызывался; `TIME_UNSET` — mix выходил сразу; пик ~0.78 тонул в барабанах. Тесты смотрели mix-буфер, не то, что уходило в `AudioTrack`. 0.3.9–0.3.19: второй `AudioTrack` (`ClickTrack`), gain 2.2 — слышно, но фаза относительно песни на BlueStacks непредсказуема. С 0.3.20 клик снова в том же PCM, **после** WSOLA, в копии, которую sink точно играет; `CLICK_VOLUME` 2.2 + limiter; mime AAC на sink всё равно PCM 16-bit.

## Почему 0.3.3 глох при движении слайдера метронома

Каждый тик слайдера звал `setPlaybackSpeed`. DefaultAudioSink на Sonic сначала drain (`queueEndOfStream`). На **снижении** скорости Sonic отдаёт больше PCM, drain не успевает, `handleBuffer` вечно false. Звук пропадает, `playWhenReady` уже true, Play ничего не делает, пока не `load()` (смена таба). Сейчас скорость на AudioTrack (без drain), плюс гейт: не чаще ~100 мс, последний BPM не теряется. Фикс строки «Темп» из 0.3.3 на месте.

## Почему 0.3.2 падал при правке строки «Темп»

Первый символ в поле оригинального BPM (не слайдер). «120»→«1»/«12» парсилось как число и подставлялось в диапазон соседнего слайдера: для 12 это **30..24**. `coerceIn` с min>max — force-close. Сейчас черновик локальный, в плеер уходит по Done/unfocus, и только 30–240.

## Почему 0.3.1 ломал метроном

1. **Клики не на долях.** Сетка считалась через `ceil` в `double` плюс `remainderIndex` через границу буфера: клик доигрывался с кадра 0 **и** в том же буфере стартовал заново. Доли плыли относительно `presentationTimeUs`. Сейчас [BeatClock]: целые микросекунды от t=0 по **original BPM**. Клики мешаются в media time **до** Sonic, поэтому после `speed = metronomeBpm / originalBpm` остаются на музыкальных битах. Handler-таймера нет.
2. **Метроном ON во время Play останавливал звук.** Пока клики выключены, sink отдавал **буфер декодера** в `DefaultAudioSink`. Sink запоминает identity (`inputBuffer == buffer`) и не принимает другой ByteBuffer, пока не доест текущий. Включение кликов подсовывало `mixBuffer` → `IllegalArgumentException` → ExoPlayer в ошибке, `play()` ничего не делает, пока не `load()` (переключение на «4 стемы»). Сейчас [MetronomePcmPipe] **всегда** копирует PCM в свой буфер, даже если клики выключены. Toggle — только флаг, без stop/prepare.

С 0.3.11 вкладки «Оригинал» нет: один ExoPlayer играет только четыре стема (`StemMixMediaSource`). Импортированный mix не ставится и не fallback. С 0.3.20 клики в том же PCM (слышны при mute всех стемов: клик не масштабируется гейном стема). Поле «Темп (оригинальный BPM)» — это темп песни, не вкладка исходника.

## Почему 0.3.12 метроном не попадал в долю

До этого клик шёл по `beats[]` детектора: каждый удар притягивался к ближайшему пику (±40 мс), плюс «раз» был длиннее и ниже остальных. На слух это не четверти и не тот BPM, что на слайдере. Плюс `ClickTrack` писал в «сейчас», а колонки играли буфер с задержкой. С 0.3.12: равная сетка, один клик.

## Почему 0.3.12 метроном хромал через несколько тактов

Автокорреляция BPM квантуется hop 512 → часто ±1–2 к истинному темпу. Сетка стартовала в доле и уезжала. Второй AudioTrack ещё и сам тикал курсор, не держась ExoPlayer. С 0.3.13 BPM = наклон `beats[]`; клик каждый chunk привязан к playhead.

## Почему 0.3.13 метроном спешил относительно 102 на экране

Две причины, обе дают интервал **короче** `60 / displayedBpm` при скорости 1.

1. OLS `beats[]` даёт 102.8, UI пишет `toInt()` → «102», сетка шла по 102.8.
2. `ClickTrack` ставил каждый chunk в `playhead + queued`. На BlueStacks `playbackHeadPosition` часто 0, очередь растёт, media-курсор бежит быстрее стены — клик ~172 BPM вместо 102, пока очередь не упрётся в крышку.

С 0.3.14 сетка = целое с экрана; курсор шагает на `mediaAdvanceUs`, очередь только для фазы. С 0.3.17 фаза = `beats[]` плюс слепой 80 мс. С 0.3.18: дробный BPM до 0.1, фаза по бочке ударных, ручной сдвиг клика; слепой +80 мс убран. Курсор = playhead, без write-ahead будущей доли.

## Почему 0.3.14 клик сбивался с доли с середины песни

`onSeek` / enable-at-t>0 обнуляли курсор в `Long.MIN_VALUE`, а `renderLayer` принимал любое отрицательное как t=0. Гонка с worker после seek рисовала сетку с начала песни, пока играет середина. Плюс `player.seekTo` асинхронный: `currentPosition` ещё старый. С 0.3.15: epoch+resync, origin = запрошенное время, UNSET не рисует нулевую сетку. На 0.3.18 после scrub клик **не потоком**, а темп/фаза уезжают и так остаются: BUFFERING считался playing, origin писался со stale playhead, очередь не flush, мелкие seek не попадали в resync. С 0.3.19: клик только на `STATE_READY`, flush+epoch на discontinuity, якорь = song time (не playhead+очередь). С 0.3.20 второго трека нет: seek = `flush` stretcher + следующий PTS — абсолютная доля с t=0. Сетка kickPhase+калибровка не едет.

## Почему 0.3.14 слайдер вверх делал «гелий»

BlueStacks HAL не принимает AudioTrack speed > 1, поэтому 0.3.8 сжимал PCM **выбросом сэмплов** (decimate) и отдавал дорожку в 1×. Это resample: 220 Гц → ~330 Гц. Sonic `setPlaybackSpeed` тон сохранял, но на снижении скорости зависал drain. С 0.3.15 вверх — WSOLA (зерно 1:1, сходство волны), период тот же, AudioTrack по-прежнему 1×; вниз — playback params ≤ 1. С 0.3.20 WSOLA на **всех** скоростях, AudioTrack всегда 1×: клик можно поставить после stretch и на 0.7, и на 1.5; Sonic и HAL speed не участвуют. Speed 1.0 — bit-exact passthrough.

## Почему клик шёл раньше бочки (галоп)

Сетка от t=0 файла + `playhead + queued/lookahead` рисовали долю **в будущем** в текущий chunk (клик, потом удар). 0.3.16 убрал write-ahead и сел на онсет `beats[]` — клик всё ещё раньше бочки. 0.3.17 добавил слепые +80 мс. На `Drunk_n_Funk` экран 105: лёгкий галоп, потом сетка **плывёт** — истинный темп не целый. С 0.3.18: шаг `60/104.6`, origin из KickGrid по drums, калибровка «Сдвиг клика, мс». Seek/enable на той же сетке.

Разбор стемов: в шапке окна больше нет длинного статуса WorkManager/HT-Demucs. Прогресс — полоска и проценты на экране разделения.

## Тесты (JVM, без эмулятора)

После правок `app/src/main` гонять **оба** (не только unit-тесты — Studio собирает APK):

```
./gradlew clean :app:assembleDebug :app:testDebugUnitTest
```

Как `vendor/bin/phpunit`: крутит JUnit на компьютере, телефон не нужен. `:app:assembleDebug` ловит то, что тесты могут пропустить (видимость `private`, ресурсы, манифест). Стрим HT-Demucs: identity overlap-add восстанавливает микс на нескольких окнах 7.8 с, последний короткий сегмент без хвоста нулей; OOM на окне модели → «короткий трек». Есть кейсы: mute на текущем mix-буфере; стемы замучены → клик всё равно в PCM, который уходит в sink; клик на ожидаемом выходном сэмпле при 0.7 / 1.0 / 1.5; атака клика не смазана WSOLA; seek → следующая абсолютная доля; limiter без wrap 16-bit; stretch 1.0 bit-exact; шаг клика = `periodSec` без пересчёта из BPM; `TIME_UNSET` не рисует t=0; фаза бочки в этом периоде, BPM ударные не складывают; слайдер сдвига по умолчанию 0 (ключ v37); `analysis.json` без `periodSec` или со старым `kickGridVersion` пересчитывается; сквозной PCM: клик минус бочка в **одном** буфере при ×1.00 / seek / середина / StemMixBank / ×0.8 / ×1.2, без роста ошибки вдоль песни. JVM не слышит колонки.

## Почему 0.3.20 клик больше не на втором AudioTrack

Второй `STREAM_MUSIC` трек (0.3.9–0.3.19) имеет неизвестную задержку относительно песни: любой сдвиг фазы — догадка, seek и скорость её ломают. Один буфер `music_after_stretch + click` сдвигает оба одинаково. Stretch нельзя отдать HAL при speed < 1 — тогда клик нельзя смешать *после* растяжения. Поэтому WSOLA в `MetronomePcmPipe` (не Media3 `AudioProcessor`: у процессора нет `presentationTimeUs`, а доли считаются от PTS `StemMixMediaSource`). `ClickTrack` / `ClickClock` / `ClickSeek` удалены.

## Почему 0.3.20 клик был на 150+ мс позже бочки

Один буфер убрал задержку устройства, но фаза сетки бралась по **пику** низкочастотного потока энергии, а не по началу онсета. У бочки с нарастанием ~150 мс (или размазанной HT-Demucs) пик на ~110–150 мс позже удара — клик садился туда. Слайдер −150 был упором, не калибровкой HAL. С 0.3.21 KickGrid откатывается по потоку влево до начала подъёма. Сдвиг клика −500…+500 мс; сохранённый −150 сбрасывается (новый ключ prefs).

## Почему на 0.3.21 всё ещё нужен сдвиг −160 мс

`analysis.json` уже лежащих треков хранит старый поздний `kickPhaseSec`. Пересплит HT-Demucs минуты, а KickGrid по drums WAV — секунды. С 0.3.22 в JSON есть `kickGridVersion`: при открытии трека и в списке библиотеки, если версии нет или она старше, сетка пересчитывается в фоне без Demucs. Кнопка «Пересчитать темп и фазу» делает то же вручную. Онсет смотрит ещё и на HF-щелчок атаки, не только на 12% низкой энергии. Слайдер и ключ prefs `click_shift_ms_v21` не трогаем.

## Почему на 0.3.23 клик всё ещё на −170 мс (два трека)

На 0.3.23 «На Титанике» и «Город 312 – Фонари» оба хотят **ровно −170 мс** на ×1.00. Это не 16-я и не фаза конкретной песни.

Сквозной JUnit гоняет синтетические удары (104.6 BPM, фаза 80 мс) через настоящие `MetronomePcmPipe` + `StemMixBank`, ищет клик и бочку **в одном выходном PCM**:

| Режим | медиана click−kick | разброс |
| --- | --- | --- |
| ×1.00 с начала / seek 2 с / середина / StemMixBank | **0.000 мс** | 0…0.023 мс (1 сэмпл) |
| ×0.8 / ×1.2 | ~0.0–0.25 мс | локально WSOLA, не 170 мс |
| импульс в песне → индекс выхода ×1.00 | **0 мс** | нет подкладки |

PTS `StemMixMediaSource` и кадр live-remix раньше расходились на **1 сэмпл** (`floor` vs `round` в `BeatClock.mediaUsToSample`) — 0.023 мс, не 170. С 0.3.24 оба конца на `BeatClock`. WSOLA на ×1.00 — passthrough, `delayFrames=0`. Logcat `ClickPipe` при старте: фаза, origin, songOffset, in/out, padFrames, delayFrames.

**Конвейер относительно клик/бочка чист.** Постоянные −170 мс на двух треках живут либо в фазе KickGrid по реальному drums WAV (не по синтетике), либо после mix на устройстве (MediaCodec raw). Слайдер не сбрасываем: 0 должен быть идеалом по PCM; −170 пока калибровка, пока не придёт logcat `KickGrid` + `ClickPipe` с телефона.

## Почему на 0.3.24 клик всё ещё на −170 мс (KickGrid timebase)

Аудит WAV → `kickPhaseSec` (не playback):

| Этап | Задержка |
| --- | --- |
| Чтение WAV / ресемплинг | **0 мс** (mmap сэмплов, фильтра нет) |
| IIR LPF 150 Гц (один полюс) | **+1.05 мс** (групповая на DC) |
| STFT | **нет** (RMS хопа 512 = 11.6 мс, не FFT) |
| Метка кадра | была **начало** окна (удар на 80 мс → 69.7 мс, **−10.3 мс**) |
| Сглаживание flux 3-tap | 0 (потом откат к 12% энергии) |
| Кадр = конец окна | **не используется** |

Сумма **поздних** систематических задержек: **1 мс**, не 170. С 0.3.25 метка хопа — **центр** окна (ошибка ≤ 5.8 мс). `kickGridVersion` = 3 — автопересчёт. Реалистичная бочка через тот же путь, что кнопка: ошибка фазы ≤ 10 мс. Logcat `KickGrid`: `firstPeak`, `energyStart`, первые 8 четвертей `t/start/peak`. Если на реальном drums WAV `firstPeak` ≈ `energyStart`+170 мс — это данные стема, не фильтр. Проверка без телефона: положить `stems/drums.wav` в тест, `WavReader.readStereo` + `KickGrid.refine`, сравнить фазу с ударом на слух/в Audacity. Слайдер не сбрасываем.

## Почему на 0.3.26 клик всё ещё на −170 мс (щелчок до тела)

Logcat «На Титанике», KickGrid version=3: `firstPeak=+52ms energyStart=+52ms`, почти все онсеты `bin=Q`, шаг ~0.57 с. Низ и пик совпадают — это не 16-я и не 1 мс фильтра. Слышимый удар ~170 мс **раньше** этой точки. Строка `quarters:` врала: `wrappedDistance` по периоду выбирал один и тот же онсет на q0..q7 (у всех start=+621ms).

С 0.3.27: start/peak квартала — ближайший онсет **по абсолютному времени**. Для сильных низких онсетов на четвертях ищем короткий всплеск полной полосы / >150 Гц в окне 80–220 мс до него. Если он устойчиво есть (большинство четвертей, разброс ≤25 мс) и это **не** 16-я сетки — фаза по щелчку, `kickGridVersion` 4. На синтетической 70 Гц бочке и на реалистичном глиссандо (щелчок на теле, не за 170 мс) прекурсора нет, фаза остаётся на низком онсете. −170 в сетку не зашит. Logcat: `earlyClick hits=N/M medianLead=… used=true/false`.

## Почему 0.3.28 падало на Skyfall (RAM HT-Demucs)

Adele — Skyfall (~5 мин) и другие длинные песни: весь микс float32 плюс 4 стема той же длины плюс сессия ONNX. Сообщение «Не хватило RAM для HT-Demucs. Попробуйте более короткий трек.» Ручная обрезка не нужна. С 0.3.29 исходник пишется в `mix44100.wav` на диск, HT-Demucs берёт кусок **30 с**, перекрытие **2 с**, линейный кроссфейд, стемы дописываются в WAV. В RAM — текущий кусок и хвост 2 с. При OOM на куске размер 20→15→10→**7.8 с** (окно модели) и проход сначала. Текст про короткий трек — только если не влез даже кусок 7.8 с. Один файл, как раньше.

## Почему на 0.3.29–0.3.31 вместо музыки были помехи

Телефон на **0.3.28** играет чисто: один overlap-add окон HT-Demucs 7.8 с на весь микс. 0.3.29, чтобы влезть в RAM, резала mix на **30 с**, гоняла `HtDemucs.separate` (уже со своим окном и паддингом нулями) и склеивала линейным кроссфейдом 2 с. Identity-склейка совпадающего overlap на синусе проходит, но это не то же самое, что внутренний overlap-add 0.3.28: у каждого 30-секундного куска последний внутренний сегмент — короткий хвост аудио + ~7 с нулей, плюс второе окно поверх уже оконченного. С 0.3.32 снова окна **7.8 с**, аккумулятор только на один сегмент, готовый STRIDE сразу на диск. Stretch 1.0 по-прежнему passthrough и ни при чём.

## Почему 0.3.33 считает темп как beat-sense

Старый novelty/autocorr с гармоническим бонусом любил октаву (Skyfall 153, весна 155). beat-sense `tempoOfTrack` на файле точнее: поток спектра до **2.8 кГц**, вычитание локального среднего, автокорреляция **55–210**, выбор октавы (порог **0.48** вниз выше зоны 145, **0.7** вверх только в **85–145** при сильных offbeat), фаза по огибающей, **refineTiming ±1.5%**. Микрофонный `tempo.ts` / AudioWorklet / акценты клика не переносим: клик по-прежнему один короткий щелчок в общем PCM после WSOLA. KickGrid остаётся для фазы бочки. Склейка Demucs 7.8 с и сдвиг **−180 мс** как в 0.3.32.

## Почему 0.3.33 на Skyfall давал 77, а beat-sense 75

0.3.33 собирал `tempoOfTrack` по именам функций: Origin git-keeper ответил 401, исходник `lib/track-tempo.ts` не читался. Угаданные тела: кража пика в зоне 85–145 при 90% высоты, сырая автокорреляция (короткий лаг = более быстрый BPM), comb-поиск периода **±1.5%**. На Adele это садится на **77** (часто 154/2). С 0.3.34: корреляция Пирсона, лог-гаусс вокруг 120, парабола по трём бинам, refine только соседний хоп и фаза. С 0.3.35 тела из `internal/beat-sense/track-tempo.ts`, не угаданные. Клик, WSOLA, Demucs 7.8 с и сдвиг **−180** не трогаем.

## Почему 0.3.35 — их файл, не «по мотивам»

В сторе лежат `track-tempo.ts` (485 строк) и `track-tempo.test.ts` (224). Порт: decimate 16 кГц, nfft 512, hop 10 мс, low 40–200 + mid до 2.8 кГц, окна 12 с / шаг 3 с, семья октав 0.25…4, старт с самого медленного, удвоение только при offbeat 0.48 (0.7 если 85–145 и быстрее 185), OLS refine ±1.5%. `demo-rhythm.ts` в сторе нет — демо-кейсы бьют бочкой в `start`. KickGrid, клик, WSOLA, Demucs 7.8 с, −180 не трогали.

## Почему 0.3.36 сетка только TrackTempo

На 0.3.35 `tempoOfTrack` уже давал дробный BPM, точный период и `phaseSec` микса, но StemSplitWorker после Demucs и кнопка «Пересчитать темп и фазу» всё ещё звали `KickGrid.refine` по drums.wav: другой BPM (в том числе складка 150→75) и фаза бочки поверх. Плеер шагал `60 /` BPM после округления до 0.1. С 0.3.36 клик читает `periodSec` и `phaseSec` из `analysis.json`; `MetronomeClickEngine` берёт интервал и начало сетки оттуда. KickGrid остаётся разбором ударных. Клик один, в общем PCM, WSOLA, Demucs 7.8 с, сдвиг **−180** как были.

## Почему 0.3.37 фаза с drums, сдвиг снова 0

0.3.36 забрал сетку у KickGrid целиком: `phaseSec` был фазой микса `tempoOfTrack`, не бочки. Слайдер по умолчанию −180 закрывал долю руками. С 0.3.37 микс по-прежнему пишет `periodSec` и BPM; следом по drums.wav считается **только фаза** в этом периоде (`kickGridVersion` 9). BPM ударные не выбирают и не складывают 150→75. Слайдер «Сдвиг клика» — ключ `click_shift_ms_v37`, дефолт **0**; −180 с v28 не подхватывается. Это запас на задержку аппарата. Клик один, шаг = `periodSec`, WSOLA и Demucs 7.8 с как были.

## Почему 0.3.39 клик плыл и каждый раз на разное время

Это не постоянные −170 мс. На 0.3.37/0.3.38 сетка пересчитывалась во время игры:

1. **`TIME_UNSET` → t=0.** После seek/flush sink иногда отдаёт буфер без PTS. Клик рисовался как начало песни, а стемы уже в середине. Сдвиг = текущий playhead, каждый seek другой.
2. **Шаг из округлённого BPM.** `originalBpm` после `refreshKickGrid` вызывал `refreshGridOrigin`; без `periodSec` шаг становился `60/bpm` до 0.1 — сетка уезжала от микса.
3. **WSOLA искал зерно по содержимому.** Стемы локально сжимались не с тем коэффициентом, с каким клик ставился линейно `out/in`. Ошибка копилась и зависела от сигнала.

С 0.3.39: один `periodSec` и одна `phaseSec` на трек (`setAnalysis` фиксирует интервал; BPM его не трогает). `TIME_UNSET` клик не рисует. WSOLA шагает тем же `outFrames/inFrames`, без `bestMatch`. Слайдер сдвига по-прежнему 0, шаг клика = `periodSec`.

## Почему 0.3.40 клик сразу невпопад на 500 / 180 мс

На свежей 0.3.38/0.3.39 `kickGridVersion` 10, `phaseSec` совпал с сеткой микса: Skyfall **0.576448941793** (слышно ~500 мс — почти сама `phaseSec`), «На Титанике» **0.075738712844** (~180 мс). Гребёнка низкой **энергии** в locked-периоде садится на тело удара / bleed микса, не на атаку бочки. Поднять версию KickGrid без смены алгоритма клик не сдвигает. С 0.3.40 `periodSec` микса тот же; `phaseSec` — онсеты бочки в этом периоде (rankPhases при bpm=60/period только для скора). Если кластер бочки на десятые в стороне от гребёнки энергии — пишем кластер. Щелчок атаки до запаздывающего тела Demucs — lookback 0.12–0.40 с. `kickGridVersion` **11**. Слайдер сдвига по умолчанию 0.

## Почему 0.3.41 клик не в бочку (слайдер ~200 мс / 0)

На 0.3.40 стем ударных не даёт стабильную фазу: Demucs сажает тело позже слышимой атаки микса, HF-откат по drums угадывает мимо. Слайдер ~200 мс на одной песне — не калибровка HAL. С 0.3.41 `periodSec` микса тот же. Сравниваем атаку микса (гребёнка потока) и тело drums в этом периоде. Если тело стабильно позже — `phaseSec` с атаки микса. Лаг измеряется по ударам, не константа 200 мс. Если задержки нет (вторая песня, слайдер 0) — фаза стема. `kickGridVersion` **12**. Слайдер сдвига по умолчанию 0.

## Почему 0.3.42 клик попадает на одних песнях и мимо на других

Не калибровка и не громкость. До 0.3.41 прод-путь — ровная решётка `t = phaseSec + n * periodSec`: `MetronomeClickEngine.mixInto` → `paintEqualGrid`, `BeatClock` не читает `beats[]`, `TempoDetector.analyze` строит линейку, `trackBeats()` умел сдвигать долю к novelty, но `analyze()` её не вызывал, `DrumPhase.align` двигал всю сетку одним `phaseSec`. Ещё один сдвиг фазы (early-click, mix-attack, Demucs lag, `calibrationUs`) долю не чинит: на одной песне атака совпала с линейкой, на другой каждая доля живёт в своём месте.

С 0.3.42 клик из `beats[]`. После `TrackTempo` черновая сетка `phase+n*period`, каждая точка к ближайшему kick/novelty в ±0.12 периода (шаг от уже притянутой доли, иначе дрифт 120→116 уезжает за окно). Нет онсета — точка решётки. `periodSec` — средний шаг для подписи, BPM не переписываем. `align` не подменяет `beats[]` одной фазой drums. Seek и 0.85/1.15 — song time стемов; клик после WSOLA, сам не растягивается. Half/double и Skyfall-октава не трогали. `kickGridVersion` остаётся **12**.

## Почему 0.3.42 метроном включён, а щелчка нет

Не громкость и не калибровка. `mixInto` стал красить только `beats[]`. В `analysis.json` доли — **секунды**. Если их читают как µs (0.5 → 0 µs, линейка 0,1,2), `firstOverlappingIndex` в текущем PCM ничего не находит и выходит. Пустой `beats[]` должен был дать решётку, но старый JSON редко пустой — там линейка в секундах. Gain клика 2.2, не 0. Snap долей не откатывали. С 0.3.43: секунды → µs; если сетка не похожа на четверти в µs — снова `paintEqualGrid`. Клик слышен и на старом JSON с `beats[]`, и на fallback.

## Почему 0.3.43 на телефоне тихо, а юнит-тесты зелёные

Не громкость. Тесты 0.3.43 звали `MetronomePcmPipe` с буфером на 1–2 с и смотрели helper. Телефон играет **чанки StemMix 1024 кадра** через `MetronomeAudioSink.handleBuffer` → DefaultAudioSink → `AudioTrack.write(remaining())`. `mixInto` мог оставить курсор так, что клик не в remaining(), которое ест sink; либо `beats[]` выглядели как µs-сетка, но не пересекали PTS стемов — `paintBeatTimes` на каждом 23 мс chunk выходил в ноль и **не** возвращался к решётке. С 0.3.44: после paint курсор на play-region; секунды JSON переводятся там, откуда плеер кормит клик (`setAnalysis`); если доля не около текущего окна — снова равная решётка, как до 0.3.42. Тест `ClickSinkPcmTest` гоняет именно `MetronomeAudioSink.handleBuffer` и проверяет remaining() делегата.

## Почему 0.3.38 пишет phaseSec с drums, не hop микса

На 0.3.36 клик читает только `analysis.phaseSec`. `KickGrid.refine` писал `kickPhaseSec` (и мог сменить BPM), `phaseSec` не трогал — плеер оставался на фазе микса. Skyfall: `periodSec` 0.800117626775, `phaseSec` ≈ 0.528; «На Титанике»: 0.571245460987 / ≈ 0.076. Это не бочка. Нужный сдвиг — **десятые** секунды (~0.3 с раньше / ~0.19 с позже), не кадр STFT 0.012–0.016 с. С 0.3.38 `DrumPhase.align` после drums.wav: гребёнка низкой энергии в готовом периоде + старт онсета, в `phaseSec` и `kickPhaseSec`. `periodSec`/`bpm` микса. `TrackTempo.kt` и `KickGrid.refine` на пути плеера не вызываем. Слайдер сдвига = 0.

## Почему на «31-й весне» метроном невпопад (0.3.28)

Песня ~**77 BPM**. Автокорреляция novelty часто побеждает октаву ~**156** (гармонический бонус к более быстрому лагу). На 0.3.28 коридор 70–180, fold баллады ещё нет — сетка 156, −180 мс не помогает: это не HAL, а двойной темп. С 0.3.31 156→78 складывается как Skyfall 153→76.5. С 0.3.32 после fold OLS по новым долям возвращает **~77.1**, не середину half(raw); KickGrid сидится уже со сложенной октавы. `kickGridVersion` = 7. 104.6 / Skyfall 76.5 не трогаем.

## Почему Skyfall на 0.3.29 стала 131 BPM вместо ~75

Песня ~73–76. Детектор часто видит **65.5** (8/9 от 73.7). Старый коридор half/double был **70–180**: всё ниже 70 удваивалось, 65.5→**131**. KickGrid после стемов перезаписывал BPM микса этим 131, и все онсеты «идеально» садились на каждую вторую четверть быстрой сетки — штрафа за пустые доли не было. С 0.3.30: коридор **60–180**, 65.5 не удваиваем; KickGrid выбирает более медленный BPM, если заполненность сетки близкая; `refine` оставляет BPM микса, если drums — октава / 8/9 / 2×8/9 от баллады.

После 0.3.30 Skyfall стала **153** (= 76.5×2): и mix, и drums уже удвоены, `preferMix` их не разводит. С 0.3.31 пульс **140–180**, у которого половина в 60–90, складываем обратно (153→76.5, 150→75). 104.6 / 120 не трогаем. С 0.3.32 `kickGridVersion` = 7 — автопересчёт по существующему drums WAV (сид KickGrid уже со сложенной октавы, OLS после fold). С 0.3.33 файловый BPM считает `TrackTempo` как beat-sense; KickGrid больше не подменяет его октавой. `kickGridVersion` = 8. 0.3.33/0.3.34 угадывали тела функций. С 0.3.35 — порт `track-tempo.ts` из стора, функция в функцию. Слайдер сдвига клика не трогаем.

## Почему на 0.3.27 слайдер всё ещё −170…−180 (калибровка устройства)

KickGrid version=4, `earlyClick used=false`, фаза ~+50 мс: сетка не нашла щелчок за 80–220 мс до низа. На BlueStacks две песни попадают в бочку около −170…−180 — это не анализ, а задержка устройства относительно PCM. С 0.3.28 дефолт слайдера **−180 мс**, ключ prefs `click_shift_ms_v28`. Старый `click_shift_ms_v21` (0 или −170) **не читаем**: после обновления все стартуют с −180. Смысл шкалы тот же: 0 — как в анализе, минус — раньше. Кто подвинет слайдер — сохранится уже новый ключ.

## Почему 0.3.25 не собиралось в Android Studio

`MetronomePcmPipe` читает `clickEngine.kickPhaseUs` для строки logcat `ClickPipe`. В копии Studio свойство снова стало `private var` (запись только внутри класса). Unit-тесты крутились из `/tmp` по уже скомпилированному публичному геттеру и `:app:testDebugUnitTest` не пересобирал APK. С 0.3.26: `var kickPhaseUs … private set` (читать можно, писать только engine) плюс JUnit, который это читает. После правок main обязателен `:app:assembleDebug`.

## Почему на 0.3.22 клик всё ещё на −160 мс (Drunk_n_Funk)

Пересчёт KickGrid по drums WAV **не сдвинул** фазу: это не устаревший JSON. −160 мс ≈ одна 16-я (143 мс при 104.6) плюс ~17 мс. Круговая средняя всех онсетов (бочка на 1 и на «a» двойки, малый с низким телом, bleed баса) садится на синкопу / на 16-ю позже доли. С 0.3.23 фаза выбирается по **сильным бочкам на четвертях** (короткая атака, мало 100–250 Гц), кандидаты с шагом 16-й, штраф за e/a. `kickGridVersion` = 2 — автопересчёт ещё раз. В logcat тег `KickGrid`: bpm, фаза, top-5 кандидатов, первые 24 онсета. Слайдер не сбрасываем.

## Скопировать и собрать APK на Windows

Код лежит в store Cursor. Studio у вас часто открывает копию, например `c:\Users\zador\rehearsal`.

1. Скопируйте **всю** эту папку (там, где `settings.gradle.kts`) поверх копии Android Studio.
2. File → Sync Project with Gradle Files.
3. **Build → Generate App Bundles or APKs → Generate APKs** (debug).
4. Поставьте новый APK **0.3.44**. Плеер — только стемы. Длинный трек разбирается окнами 7.8 с на диск, без 30-секундной склейки. На `Drunk_n_Funk` original BPM должен быть около **104.6**. На Skyfall — **75**, клик из `beats[]` (не одна `phaseSec` 0.576). На «На Титанике» — **105**. Сдвиг клика **0**. Метроном ON — слышный щелчок. Слайдер **вверх и вниз** меняет темп без гелия и без Sonic drain.

Если Kotlin-демон падает (`kotlin compile daemon is ready`) — в `gradle.properties` уже `kotlin.compiler.execution.strategy=in-process`.

Если Gradle пишет `kspDebugUnitTestKotlin FAILED` и `lateinit property cleanFilenames has not been initialized` — это **кэш KSP**, не метроном и не «Fix with AI». В `gradle.properties` уже `ksp.incremental=false`. Дальше на Windows:

1. Не нажимать Studio «Fix with AI».
2. **Build → Clean Project**.
3. Закрыть Studio. Удалить папку `c:\Users\zador\rehearsal\app\build`.
4. Скопировать проект из AgentStores **поверх** `c:\Users\zador\rehearsal`.
